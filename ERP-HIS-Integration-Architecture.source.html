ERP × HIS Interoperability
Technical reference · ERP–HIS partnership

Best-in-class integration technologies: this ERP × a HIS (TrakCare)

A companion to the demo speaker notes — the standards, architecture pattern, and phased path for connecting this ERP's Party / Product / Order / Facility / Accounting core to InterSystems TrakCare, without either system becoming a satellite of the other.

In one paragraph

The standards choice isn't really open anymore: HL7 FHIR R4 is the modern default, and TrakCare's own InterSystems IRIS platform already speaks it natively — plus legacy HL7 v2.x, which still carries most live ADT traffic in production HIS deployments. NPHIES is not our problem to solve at all: InterSystems is independently certified NPHIES-compliant and TrakCare already submits claims through it for live Saudi hospitals today. That removes an entire integration leg from this design. What's actually left to build is small: a thin FHIR-shaped adapter added to this ERP's existing API project, talking directly to IRIS's own interoperability engine — which already does the queuing, retries, and routing our side would otherwise have had to build from scratch.

01 Glossary — if HIS terms are new to you

Every term used on this page, in plain language, grouped by what it's actually for. Skip this section entirely if you already work in health IT.

The systems themselves
HISHospital Information System

The hospital's own software — admissions, orders, results, and clinical billing. TrakCare is one specific HIS product, made by a company called InterSystems.

EMR / EHRElectronic Medical / Health Record

The part of a HIS that holds a patient's actual chart — diagnoses, notes, medications. People often say "EMR" and "HIS" interchangeably in conversation.

ERPfor contrast

This system. Manages the business side — orders, inventory, accounting — rather than clinical care. The two systems' data has to meet in the middle.

PACS / RIS

The systems that store medical images (X-rays, scans) and run the radiology department's workflow. Mentioned only so it's clear this ERP never touches image data directly.

How systems talk to each other
HL7Health Level Seven

The umbrella name for the family of hospital messaging standards. Not one format — a whole lineage of them, including the next two entries.

HL7 v2.x

The older, still-dominant message format — plain text with fields separated by | pipe characters. Not pretty, but it's what most live hospital systems actually send today.

ADTAdmit / Discharge / Transfer

An HL7 v2 message announcing patient movement — admitted, discharged, or moved to a different ward or bed.

ORU / ORMObservation Result / Order

Two more HL7 v2 message types — ORU carries a lab or test result, ORM carries a new order such as "run this test."

FHIRFast Healthcare Interoperability Resources, said "fire"

The modern replacement for HL7 v2 — structured JSON exchanged over a normal web API, the same style this ERP's own OData endpoints already use.

Resourcea FHIR term

A named, structured record type — Patient, Encounter, Claim. Think of it as a DTO with an industry-agreed shape everyone builds to.

Matching up identity across systems
MRNMedical Record Number

The HIS's own unique ID for a patient — the hospital-side equivalent of this ERP's PartyId.

IHEIntegrating the Healthcare Enterprise

An initiative that defines standard patterns for using HL7/FHIR consistently, so two vendors' systems can actually interoperate, not just both claim "FHIR support."

PIX / PDQtwo IHE patterns

PIX keeps two systems' patient IDs cross-referenced to each other; PDQ lets one system ask the other "does this patient already exist, and under what ID?"

Saudi-specific & regulatory
NPHIES

Saudi Arabia's national platform that every hospital and insurer must connect through for eligibility checks, approvals, and claims. TrakCare already has this certified — it's TrakCare's job, not this ERP's.

PDPLPersonal Data Protection Law

Saudi Arabia's data-privacy law — governs how personal and health data must be stored, moved, and protected.

Payer

Insurance terminology for whoever is paying the bill — an insurance company, in most cases here.

Eligibility / Prior auth

Asking the payer "is this patient covered, and will you approve this treatment" — before or during care, via NPHIES.

Claim

The bill submitted to the payer after treatment is given.

Remittance

The payer's response to a claim — what they agreed to pay, and why anything was reduced or rejected.

Security
OAuth2

A standard way for one system to prove to another "I'm allowed to access this," using short-lived tokens instead of a shared password.

SMART on FHIR

OAuth2 adapted specifically for healthcare FHIR APIs — the standard way a clinical app authenticates itself.

Mutual TLSmTLS

Both sides of a connection prove their identity with certificates — not just the client checking the server, the way an ordinary "padlock icon" website connection works.

TrakCare / InterSystems specific
InterSystems IRIS

The underlying database-and-integration platform TrakCare is built on — not just a hospital app, but also the "engine room" capable of sending and receiving HL7/FHIR messages.

Interoperability engineformerly "Ensemble"

The piece of IRIS that translates and routes messages between TrakCare and outside systems, with queuing and retry already built in — the thing our FHIR adapter in §03 talks to directly, no extra infrastructure needed on our side.

Clinical/business terms used in §04's mapping table
Encounter

One clinical visit or episode — a checkup, an ER visit, a hospital stay. Roughly the HIS equivalent of an ERP order.

Coverage

A patient's insurance policy details, in FHIR form.

Practitioner / RelatedPerson

FHIR's terms for a clinician, and for a patient's family member or guardian, respectively.

ServiceRequest

A FHIR resource for an ordered procedure or test — the FHIR-shaped version of an ORM message.

ChargeItemDefinition

A FHIR resource describing something billable and its price — the FHIR-shaped version of a product/price-list entry.

ExplanationOfBenefitEOB

A FHIR resource showing what the payer decided about a claim — the FHIR-shaped version of "remittance."

03 Recommended architecture — simpler than the first draft

No new service to deploy, no event bus to run and monitor. One new set of endpoints inside this ERP's existing API project, talking straight to the integration engine TrakCare already operates.

Two systems talking directly, not three. The adapter is a handful of new controllers in this ERP's existing API project — it translates OrderRecords/PartyRecords to and from FHIR shapes, reusing the CQRS handlers that already back the OData endpoints. Everything to the right of the arrow is TrakCare's job: IRIS's own interoperability engine already queues, retries, and routes messages (confirmed against InterSystems' own documentation, not assumed), and NPHIES submission is a capability TrakCare ships with today, independently certified — not something this integration has to build.

Flow direction, in short: Party is bidirectional (ERP owns the billing party, TrakCare owns clinical identity); Product, Order, and Facility flow TrakCare → ERP (their catalog and encounters become our pricing and orders); GL flows ERP → TrakCare → NPHIES → payer, with remittance posting back the same path into the GL engine already in place.

05 Why this fits the current stack

No new service to stand up, patch, or monitor — the adapter is new endpoints in the existing API project, thin because the ERP is already shaped like a REST API, not a database dump.

OData endpoints (OrderRecords, PartyRecords, QuoteRecords) are already resource-shaped, filterable lists — the adapter translates them, it doesn't replace them.
CQRS already separates reads from writes. FHIR's own verbs map directly: GET → Query, POST/PUT → Command — no new mental model for the handler layer.
The MediatR pipeline already runs a LoggingBehavior ahead of every handler — that's the natural slot for FHIR resource validation too, without touching a single existing handler.

06 Security & compliance

Mutual TLS
