The idea in three lines

The auditor asked that financial records be marked as cancelled, never erased, and that their accounting entries be reversed rather than deleted.

Step 1 found the 19 places in the code that erase. Step 2 builds the four tools those places will use, and turns on one control: a closed accounting period is now locked.

The 19 places still behave as before. Switching them over is step 3.

The four tools

Period lock
Once a month or quarter is closed, nothing can be written into it and nothing can be deleted out of it. It checks every new entry and every delete.
Reversal
Cancels a posted entry by writing its mirror image, linked to the original. Both stay in the ledger. The same entry cannot be reversed twice.
History check
Asks one question before a delete: has this record ever touched the ledger or the bank book? If yes, it may not be deleted.
Void a payment
Marks the payment void, reverses what it posted, cancels its bank rows and detaches it from invoices. The payment stays on file.

Voiding is available to the API today. No screen calls it yet; that comes with step 3.

What a user will notice

Four refusals, each with a message that says why and what to do instead. Everything else works exactly as before.

  1. Payroll. A month cannot be deleted or re-run once its salary payment has been sent. This is the pragmatic rule you chose: free to correct before sending, settled after.
  2. Invoices. An invoice cannot be reset while a sent or received payment is applied to it. Its status history is now kept instead of erased.
  3. Sales-order payments. The delete tick is refused for a payment that has ledger or bank history.
  4. Closed periods. Any write into, or delete from, a closed period is refused. No period is closed yet, so this fires nowhere today.
What did not change. Reset still deletes and Delete still deletes on every screen. Those flips are step 3 and must arrive together with the new screen actions, otherwise users would be refused with nowhere to go.

Small fixes made on the way

  • Reset payment checked for a status name that does not exist, so a voided payment was never actually protected. Fixed.
  • An old copy-and-reverse routine reported success but lost the new entry's number. Fixed.

The database script you ran

It added the one missing "cancelled" status, for sales requests, with its allowed transitions. Nothing else in the database changed. Copy the script to the production folder when you apply it there.

The same script lists 90 bank rows that sit on payments still in draft. Checked on 14 September: they are by design. A cheque payment gets its bank row when it is created, not when it is sent, so these rows belong to their payments and need no cleanup. The "46 leak rows" in the first version of this report were a misreading.

Step 3

  1. Switch each of the 19 places to its class: Reset reverses, Delete voids, physical delete only for drafts that never posted.
  2. Add the screen actions: Void on the payment form with a reason box, Reverse instead of Delete on posted journal entries.
  3. Create monthly periods and start closing them, so the lock has something to lock.
