# GL Account Transaction Details Modal — Confirmed Ending-Balance Bug (GL 110100 / CIB)

Follow-up to `gl-110100-opening-balance-double-count-findings.md` (generated on another machine from a shared copy of `banks-trial-balance-vs-powerbi-findings.md`). That document correctly identified the symptom from two Excel exports; this document traces it to the exact line of code and rules out the hypotheses that turned out not to be the cause.

## 1. Source files re-examined

- `Transactions_110100_____________________ (7).xlsx` — 599 transaction rows, earliest **2026-01-01**
- `Transactions_110100_____________________ (8).xlsx` — 641 transaction rows, earliest **2025-09-10** (42 extra pre-period rows)

Both have an **identical header block**:

| Field | Value |
|---|---|
| الرصيد الافتتاحي (Opening) | 11,118,958 |
| المدين المرحل (Debit Carried) | 111,494,348.87 |
| الدائن المرحل (Credit Carried) | 108,151,813.97 |
| الرصيد الختامي (Closing) | 14,461,492.90 |

**Key observation:** the header is identical across both files even though the visible row lists differ by 42 rows. The header total does not depend on which rows are shown, which rules out "wrong date filter on the export" as the cause and points instead to a backend calculation bug independent of the row list.

Cross-checking the numbers:
- File (7)'s own bottom `Totals` row (raw SUM over its 599 rows): Debit 99,223,724.87 / Credit 107,717,263.97 — this is the **true** 2026-only period activity, and its final running balance (2,625,418.90) is the **true closing balance**.
- File (8)'s own bottom `Totals` row (raw SUM over its 641 rows, including all pre-period rows and the `OPENING_BALANCE` entry): Debit 122,613,306.87 / Credit 108,151,813.97.
- The 41 pre-period rows that aren't the `OPENING_BALANCE` entry itself sum to Debit 12,270,624.00 / Credit 434,550.00.
- `99,223,724.87 (true period debit) + 12,270,624.00 (pre-period, non-opening debit) = 111,494,348.87` — **exactly the header's "Debit Carried."**
- `107,717,263.97 (true period credit) + 434,550.00 (pre-period credit) = 108,151,813.97` — **exactly the header's "Credit Carried."**

So the header's "carried" totals correctly *exclude* the `OPENING_BALANCE`-typed entry (11,118,958) but *leak in* every other pre-period transaction, regardless of which row list was exported.

## 2. Root cause, confirmed in code

The modal/export is generated by `GetGlAccountTransactionDetails.Handler` in
`Application/Accounting/Services/GlAccountTransactionDetails.cs`, reached via
`API/Controllers/Accounting/TrialBalanceController.cs` →
`GET /trialBalance/{org}/{customTimePeriodId}/{glAccountId}/getGlAccountTransactionDetails`
(and the anonymous `generate...` variant used for the Excel export), invoked from
`client-app/.../GlAccountTransactionsModal.tsx`, which is opened by clicking an account code
in `TrialBalance.tsx`.

```csharp
// lines 137–161: openingDebits / openingCredits — correctly scoped
where ... act.AcctgTransTypeId == "OPENING_BALANCE"
      && act.TransactionDate <= openingCutoff   // periodStart - 1 tick

// lines 163–186: endingDebits / endingCredits — THE BUG
where ate.OrganizationPartyId == request.OrganizationPartyId
      && ate.GlAccountId == request.GlAccountId
      && act.IsPosted == "Y"
      && ate.DebitCreditFlag == "D"   // or "C"
      && act.GlFiscalTypeId == "ACTUAL"
      && act.TransactionDate <= periodEnd        // ← no lower bound, no type filter
select ate.Amount

// lines 200–201
decimal postedDebits = (decimal)(endingDebits - openingDebits);
decimal postedCredits = (decimal)(endingCredits - openingCredits);
```

`endingDebits`/`endingCredits` sum **every posted, ACTUAL debit/credit ever recorded for the account from inception through `periodEnd`** — no `TransactionDate >= periodStart`, no exclusion of `AcctgTransTypeId == "OPENING_BALANCE"`. Because `openingDebits`/`openingCredits` only capture the `OPENING_BALANCE`-typed entry, subtracting them from the unbounded `endingDebits`/`endingCredits` leaves every *other* pre-period transaction still counted in `postedDebits`/`postedCredits`, and `endingBalance` (= `endingDebits − endingCredits`, both unbounded-below) is inflated by the account's entire pre-period history.

Verified arithmetically against the export:
- `endingDebits (122,613,306.87) − openingDebits (11,118,958) = 111,494,348.87` = header "Debit Carried" ✓
- `endingCredits (108,151,813.97) − openingCredits (0) = 108,151,813.97` = header "Credit Carried" ✓
- `endingDebits − endingCredits = 122,613,306.87 − 108,151,813.97 = 14,461,492.90` = header "Closing Balance" ✓

**Why the "Include transactions before period" checkbox doesn't fix it:** `includePrePeriodTransactions` (lines 114–128) only filters `transactionsQuery`, i.e. which rows populate the visible grid/export list. `openingDebits`, `openingCredits`, `endingDebits`, `endingCredits` — the source of the header figures — are computed by four separate, unconditional queries that never reference this flag. Toggling the checkbox changes what you see in the row list; it never changes the header totals. This is exactly what the two files show: different row counts, identical (wrong) header.

## 3. What is *not* the cause

- **Not** a missing/stale `OPENING_BALANCE` entry — it exists, is dated correctly (2025-12-30), and is correctly excluded from `openingDebits`/`openingCredits`.
- **Not** a Power BI / `Fact_GL_Transactions` view issue — unrelated code path.
- **Not** the Trial Balance top-level grid — `GetTrialBalanceReport.cs` → `AcctgReportsService.ComputeGlAccountBalanceForTimePeriod` computes period debits/credits directly with `TransactionDate >= periodStart && TransactionDate <= periodEnd` (both bounds), and is correct. The client's trust in the Trial Balance grid itself is well-founded; only this specific drill-down modal/export is wrong.

## 4. Sibling handlers checked — not affected

- `GetBalanceSheetGlAccountTransactionDetails.cs` — `periodDebits`/`periodCredits` are computed by summing the already correctly-bounded `transactions` list directly (`transactions.Where(t => t.DebitCreditFlag == "D").Sum(...)`), not via a subtraction of two unbounded cumulative queries. Correct.
- `GetIncomeStatementGlAccountTransactionDetails.cs` — same pattern, also correct.

Only `GetGlAccountTransactionDetails.cs` uses the "cumulative-to-end minus cumulative-to-open" pattern, and it's the one place that pattern breaks down (because the two cumulative queries use inconsistent bounds — one type-filtered, one date-filtered-only).

## 5. Suggested fix

Mirror the pattern already proven correct in `ComputeGlAccountBalanceForTimePeriod` (Trial Balance) and in the two sibling handlers: compute period debits/credits directly, bounded on both sides, instead of subtracting two differently-scoped cumulative sums.

```csharp
// Replace endingDebits/endingCredits + the subtraction with:
var periodDebits = await (
    from ate in _context.AcctgTransEntries
    join act in _context.AcctgTrans on ate.AcctgTransId equals act.AcctgTransId
    where ate.OrganizationPartyId == request.OrganizationPartyId
          && ate.GlAccountId == request.GlAccountId
          && act.IsPosted == "Y"
          && ate.DebitCreditFlag == "D"
          && act.GlFiscalTypeId == "ACTUAL"
          && act.TransactionDate >= periodStart
          && act.TransactionDate <= periodEnd
    select ate.Amount
).SumAsync(cancellationToken);
// same for periodCredits with "C"

decimal postedDebits = periodDebits;
decimal postedCredits = periodCredits;
decimal endingBalance = isDebit
    ? openingBalance + postedDebits - postedCredits
    : openingBalance + postedCredits - postedDebits;
```

**Spot-check after the fix:** for GL 110100 over the 2026-01-01 → 2026-07-12 window, Opening should stay 11,118,958, Debit Carried should become 99,223,724.87, Credit Carried 107,717,263.97, and Ending Balance 2,625,418.90 — matching file (7)'s own row-level totals exactly.

## 6. Follow-up: this fix alone broke non-bank accounts — see the broader-impact doc

Applying only the period-bound fix above (no conditional) to dev and comparing it against
production for GL `1211001` (a customer receivable sub-account with no `OPENING_BALANCE` entry)
showed the fix producing a **negative** Ending Balance (-3,350,986) that contradicted the
account's own transaction grid, which independently confirmed the correct value was 16,795,409
(production's number). The final fix adds a per-account conditional — bound to
`[periodStart, periodEnd]` only when the account has an `OPENING_BALANCE` entry; otherwise fall
back to the lifetime-to-date total. Full detail, including the dev/prod comparison and the
account classification behind the decision, is in
`gl-account-transaction-details-broader-impact-scan.md`.

**Applied.** `Application/Accounting/Services/GlAccountTransactionDetails.cs` now computes `periodDebits`/`periodCredits` bounded by `TransactionDate >= periodStart AND <= periodEnd` (replacing the unbounded-below `endingDebits`/`endingCredits`), and `endingBalance = openingBalance ± postedDebits/postedCredits`. Not yet built/run — per project convention, code changes are reviewed and verified by the developer, not auto-built by the assistant.
