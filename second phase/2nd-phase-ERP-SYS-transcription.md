# متطلبات المرحلة الثانية — نص القائمة المكتوبة بخط اليد

نسخة نصية من الملف `2nd phase ERP SYS updated.pdf` (٦ صفحات، بتاريخ ٢٩ يوليو ٢٠٢٦).
الترقيم والصياغة كما وردت في الأصل قدر الإمكان. المصطلحات الإنجليزية مكتوبة كما كتبها العميل.
المواضع غير الواضحة في الخط موضوعة بين ⟨ ⟩ مع أقرب قراءة لها.

## الصفحة ١ — التقارير والنظام عمومًا

- إنشاء محرك خاص بالتقارير + **Custom Report** تفصيلي حسب الطلب.
- تقارير القسم محتاجة تظبيط ⟨تراكم⟩ الأعمال والميزانية، مع وجود مستويات لعرض التقرير ((**Subtotal**)).
- ★ إضافة أكثر من شركة (جولدن / الأرض القابضة).
- ★ **DMS** — ربط ⟨السيستم⟩ بالمستندات المرفقة، مع كل رقم دفعة يتم الوصول إليها بضغط رقم الدفعة.
- ★ **PDC Management** — ملاحظة هامشية: ⟨شاشة خاصة بالشيكات: استحقاق / الدفع / مرتجع⟩.
- مشاكل التقارير: يضاف زر للطباعة يتم توجيه طباعة التقرير بدون الحاجة إلى التعديلات في الفورمات وحجم الصفحة، زي سند الصرف والقبض.
- إضافة شاشة للتحويلات بين الحسابات البنكية والخزينة، مثلًا من CIB إلى ADIB، أو من الخزينة إلى CIB.
- أنواع الدفعات محتاجة إعادة تعريف.
- إظهار القيود اليومية مدين ودائن في شاشة الصرف والقبض قبل الإنشاء.

## الصفحة ٢ — العرض والطباعة والأتمتة

- إجمالًا طريقة العرض والطباعة محتاجة تحديث لتظهر بصورة احترافية، وكشوفات الحساب ⟨محتاجة⟩ وجميع الأشكال المصدرة محتاجة إعادة فورمات وترتيب الأعمدة لتظهر بشكل ⟨…⟩ كشف حساب البنك، ليتم طباعتها مباشرة دون إجراء تعديلات في كل مرة.
- ٢) أي معاملة يتم طباعة إيصال لها مباشرة من المعاملة دون الحاجة إلى تصدير إلى إكسل، زي سند الصرف.
- ٣) التقارير **Automation** — تحدث تلقائيًا بدون تدخل. على سبيل المثال تقرير يومي يتم تصديره بالمدفوعات والمقبوضات المستحقة خلال فترة زمنية (اليوم / أسبوع / شهر / ربع سنوي).

## الصفحة ٣ — سندات الصرف والقبض

ملاحظة في رأس الصفحة: ⟨إضافة خيار شيك مستبدل مع الاحتفاظ بالمعاملة — مع إضافة حالة مستبدل إلى مرسل أو غير مدفوع⟩.

1. عند تكرار الدفعات يكون الطرف ونوع الدفعة قابلة للتعديل.
2. عند إلغاء الدفعة يتم إضافة خيار إلغاء الدفعة إلى قائمة الإجراءات، مع الاحتفاظ بالدفعة الملغية على السيستم وتلوينها باللون الأحمر.
3. معالجة تطبيقات الدفع لتسمح بالدفع الجزئي، بحيث يظهر مبلغ المستحق للصرف والمبلغ المصروف فعليًا والمبلغ المتبقي.
4. عمل شاشات لتعديل أو حذف مركز التكلفة.
5. طريقة عرض الشاشات الرئيسية لكل سندات الصرف والقبض تحتاج إلى إعادة هيكلة لعرض جميع الأعمدة بدون التنقل يمينًا ويسارًا.
6. طباعة الإيصالات محتاجة تعديل لتتم الطباعة بطريقة احترافية، وشكل الإيصال يكون كما النموذج المرسل إليك.
7. مطلوب تقارير يومية:
   - الحركات اليومية للخزينة النقدية: رصيد أول اليوم + الحركات المدينة / الحركات الدائنة = رصيد آخر اليوم.
     ★ إضافة عمود تاريخ إنشاء المعاملة + تاريخ الموافقة على المعاملة.
   - الحركات اليومية الإجمالية لكل موظف — **Daily Activity Report** — من أول login، مع إظهار المعاملات التي تم الموافقة عليها.
8. إضافة شاشة للمعاملات التي تحتاج إلى موافقة في شاشة الصرف وشاشة القبض — **Approval Q**.
9. الفلاتر في الشاشة الرئيسية تحتاج المراجعة لإضافة **Date range** وإمكانية استخدام أكثر من فلتر، مع تفعيل الترتيب زي حالة الاستحقاق.

## الصفحة ٤ — القيود اليومية / الرواتب والسلف

### القيود اليومية

1. تقرير يومي بكل القيود التي تم تحريرها من قبل الموظف.
2. الصلاحيات في القيود تكون زي سندات الصرف والقبض.
3. طريقة عرض الشاشة الرئيسية المفروض تبين رقم الدفعة / الفاتورة لأي قيد يتم إنشاؤه تلقائيًا.

### الرواتب والسلف

1. إمكانية الترتيب والفلترة بالاسم أو القسم أو المبلغ، والبحث.
2. إمكانية تعديل الفاتورة لموظف (لحدث تغيير في ⟨البيانات⟩ والقيود) بدلًا من حذف كل الموظفين وتحريرها مرة أخرى.
3. إضافة الرصيد ⟨المتقدم⟩ مع الإجازات والرصيد المستحق.
4. إمكانية تعديل السلف — مبلغ الاستقطاع الشهري — بعد الاتفاق.

⟨بنود فرعية تحت السلف — الترقيم يبدأ من جديد في الأصل:⟩

1. إمكانية وإضافة إعادة التعيين لتعديل أو زيادة بعد الاتفاق.
2. عند الضغط على المبلغ ⟨المستحق⟩ يعرض ويطبع الحركات ⟨المستخدمة⟩ — كشف حساب.

### ⟨السلف المقدمة⟩

1. إمكانية عرض أرقام السندات ⟨المقدرة⟩ ومبالغها في شاشة سندات الصرف.
2. **Approval Q** للمعاملات المطلوب الموافقة عليها.

## الصفحة ٥ — المبيعات

1. الدمج مع الواتس لإرسال رسائل مختلفة للعملاء بالأقساط المستحقة: تذكير بمواعيد الاستحقاق قبلها، ورسائل للأقساط المتأخرة أو ارتداد الشيكات.
2. إمكانية تعديل بيانات في طلبات المبيعات دون حذف كل الدفعات السابقة، مثل تعديل التاريخ.
3. الاحتفاظ بطلب المبيعات وإمكانية تغيير العميل أو تعديل الدفعات في حالة بيع الوحدة، أو زيادة مبلغ البيع في حالة زيادة المساحة مثل الروف بعد الحصول على ترخيص.
4. إمكانية ومرونة تغيير الدفعات وإعادة هيكلتها، مع وجود إمكانية لدفعات مختلطة: شهرية + ربع سنوية + سنوية.
   - ⟨٥أ⟩ إضافة المصاريف / الضرائب المحملة على المشروع إلى تقرير المشروع.
5. مبلغ العمولة يتم محاسبته حسب الملف المرسل سابقًا، ويكون رقم الوحدة هو الأساس مع إمكانية صرف العمولات لطرف أو أكثر في كل مرة. وعند البحث برقم الوحدة يتم معرفة ما تم صرفه والمبلغ المستحق والمبلغ المتبقي للصرف وإجمالي العمولة.
6. تقرير شامل للمبيعات يشمل **Sales R** + إيرادات ⟨مستحقة⟩ ⟨…⟩ والمبلغ المطلوب توريده للضرائب، مع ربط بالفاتورة الإلكترونية.
7. طريقة لتحويل الدفعات المستلمة قبل طلب المبيعات إلى جزء من الدفعة المقدمة بعد إنشاء طلب المبيعات.

## الصفحة ٦ — المستخلصات

1. إضافة العقود مع كل مقاول أو مورد مع ربطها بالمشروع: قيمة التعاقد — المبالغ المدفوعة — المبالغ المتبقية.
2. إضافة نسب الإنجاز التراكمية. المثال المكتوب في الأصل:

   | المبلغ التعاقدي | المقاول | نسبة الإنجاز الحالية | المبلغ المستحق | المدفوع | المتبقي |
   |---|---|---|---|---|---|
   | ١٠٬٠٠٠ | × | ٪٢٠ | ٢٬٠٠٠ | ٢٬٠٠٠ | ٨٬٠٠٠ |
   | ١٠٬٠٠٠ | × | ٪٣٠ | | | |

   نسبة الإنجاز ← الحالية / السابقة / إجمالي نسبة الإنجاز (٪١٠ / ٪٢٠ / ٪٣٠).
   المبالغ ← الحالية / المدفوع سابقًا / المتبقي.

3. ربط مستخلصات لكل مشروع — **Bud vs. Actual** — يتم مطابقة جميع المصروفات بالمبلغ المستخدم.
4. ربط مستخلصات لكل مقاول أو مورد بقيمة عقد المقاولة مع المشروع.
5. توسيع حقل الوصف داخل البنود (**w/ text**) لعرض الوصف بالكامل.
6. عند تغيير وحدة القياس يتم ⟨تتبعها⟩ — ⟨مطلوب التتبع⟩.
