02The five-track plan

Authored 2026-07-17 in the now-deleted session. Track letters are labels, not a sequence — the sequencing note follows the cards.

APartly actionable today

Consolidate, don't replace

Enforce the Kendo/MUI split CLAUDE.md already states rather than changing it — both are genuinely load-bearing, and picking a winner would be a rewrite. Instead, write down which kit owns which job: Kendo for grids, form fields, dropdowns; MUI for layout, typography, dialogs, buttons — so new screens stop guessing. Then remove the strays: delete Mantine, retire Semantic UI and jQuery, finish Formik → react-hook-form, pick one of lodash/underscore.

BOngoing, by attrition

One data layer, enforced going forward

RTK Query exclusively for new features. Migrate MobX and agent.ts call sites feature-by-feature as those features get touched for other reasons — explicitly no dedicated big-bang migration.

CNot started

Wire up real-time on a low-stakes feature first

Build one hub end-to-end — order-status or approval-queue updates: hub → RTK Query cache invalidation over the socket → UI updates with no manual refresh — before any HIS event stream needs that same pattern under deadline pressure.

DNot started

A design-token and component layer, not a rewrite

Menu-Exit, Actions-Menu, and the Status Ribbon are well-specified in CLAUDE.md but exist only as documentation plus a few reference implementations. Promote them to real shared components with one implementation each, plus a small design-token set — spacing scale, one date-picker, one confirmation-dialog pattern — layered on the retained Kendo+MUI pair. A lightweight Storybook for just these shared pieces.

ENot started

Give BI/EPM somewhere to render

No charting library exists in the project at all. Add @progress/kendo-react-charts — it leverages the existing Kendo license and grid investment rather than introducing a sixth UI dependency. Needed for FIN-BUD / EPM-CPM work regardless of HIS timing.

Sequencing as originally proposed

Tracks A and B are foundation-clearing work meant to start immediately and in parallel with backend work, not gated on any HIS decision. Phase 0 (~4–6 weeks) was: delete Mantine, scope the Semantic UI / jQuery retirement, publish the Kendo-vs-MUI ownership rule, build the first real SignalR hub, and stand up Storybook for the three shared components.

04Backend architecture review

Asked on 2026-08-06 as: "deep, honest advice on the backend architecture I'm currently using and how it compares to best practices… I hear about DDD and other design patterns." Context given at the time: a single developer, a paying client, and a steady stream of bug tickets.

What's genuinely good — keep it

The CQRS/MediatR skeleton. Thin handlers (CreateSalesOrder.cs is 91 lines), Result<T> instead of exceptions-as-control-flow, per-handler transaction scoping, FluentValidation wired via AddValidatorsFromAssemblyContaining. This is not the bug source.

The anemic domain model is fine

All 892 Domain/ entities are pure data bags — a deliberate 1:1 mirror of the OFBiz schema, and a legitimate choice for a port. The problem isn't that it's anemic; it's where the logic that would live on those entities ended up instead.

The god-service problem — the actual bug source

These are modules pretending to be classes. Changing one method in a 6,000-line file, with no test around it, to fix a client-reported bug is exactly the shape of change that breaks something else three screens away — which matches the reported symptom.

Circular dependencies

Eight files in Application/ use Lazy<T> injection to resolve circular service dependencies — GeneralLedgerService, PaymentHelperService, InvoiceUtilityService, CostService, InventoryService and others. That's DI fighting a layering violation: bidirectional calls with no clear dependency direction. Each is a place where a change in A silently breaks B.

Testing is effectively zero — not "one test"

BusinessTest/Order/Orders/CreateSalesOrderTests.cs is still the only test file in the solution. It builds DataContext against a real local MySQL with hardcoded credentials, and passes null for four of OrderService's constructor dependencies — so any path touching those throws NullReferenceException unrelated to the behavior under test. It gives false confidence.

The DDD verdict — recommended against, wholesale

Full textbook DDD (aggregate roots enforcing invariants, bounded contexts, domain events) or a Clean/Onion rewrite is months of high-regression-risk work with 892 foreign-schema entities, one developer, and live client tickets. It would make the bug bombardment worse before it got better.

Worth stealing cheaply, though: value objects for Money / Quantity / currency pairs — killing wrong-currency and unit-mismatch bugs at compile time instead of at 2am when a GL imbalance surfaces, as a pure Application-layer addition with no schema change. And a thin behavior layer on two or three bug-prone areas only — order status transitions and GL posting rules — so "this transition is valid only from these states" lives in one place instead of being reimplemented ad hoc across OrderService / OrderHelperService.

Priority order as recommended

  1. Fix the test story before refactoring anything. Real isolated tests — EF Core InMemory or SQLite in-memory, fully mocked collaborators, no nulls, no real MySQL — around GL posting, order status transitions, and payment application first. Highest blast radius.
  2. Characterization-test-before-fixing, as a habit, not a project. On the next bug in GeneralLedgerService or OrderHelperService: pin the surrounding correct behavior in a test before the fix, then leave the test in. The suite grows for free alongside work that's happening anyway.
  3. Add a MediatR ValidationBehaviour. Today LoggingBehavior is the only pipeline behavior, so validation fires only through the MVC auto-validation filter on HTTP-bound requests. Centralizing it validates every command identically regardless of entry point.
  4. Strangle the god-services opportunistically — the same rule as the MobX → Redux migration in CLAUDE.md. When you're already in one of these files for a bug, extract just the methods you touched into a smaller named class with a test. Never schedule "break up GeneralLedgerService" as its own project; it will never win against client tickets and doesn't need to.
  5. Resolve the Lazy<T> circular deps as you touch those eight files, not proactively. Each is a signal that one call should go the other direction, not a symptom needing a DI redesign.

Explicitly rejected

✕Retrofitting a repository / Unit-of-Work layer over DataContext — CLAUDE.md rejects it deliberately, and it wouldn't touch the actual bug source.
✕Chasing a coverage percentage.
✕A DDD / Clean Architecture rewrite.

06Ground rules for any ERPv2 work

From CLAUDE.md, enforced:

  • Never run dotnet build / run / watch, or npm run build / start after edits. Make changes, stop, report — the developer re-runs manually.
  • Never apply an EF migration. Generating migration files or a SQL script for review is fine; applying is human-only.
  • No repository layer — DataContext injects straight into handlers. Lazy loading is off; use explicit joins or .Include().
  • Domain entities live flat in Domain/, string IDs from the OFBiz heritage, snake_case JSON. DTOs stay PascalCase.
  • Handlers return Result<T> / Results<T> — never throw.
  • OData list endpoints must be registered in Program.cs GetEdmModel().
  • // REFACTOR: comments mark known debt — don't delete one without addressing the cause.
  • Prefer RTK Query and Redux for new work; MobX and agent.ts are legacy by design.
  • Arabic localization via getTranslatedLabel and @ar.json must always be supported.
  • Do not spawn subagents in this repo unless asked.
