1   Read this first

This application applies migrations automatically on startup. API/Program.cs:194 calls context.Database.MigrateAsync(), followed by SeedContracts.SeedData(...) at line 198. Deploying the code IS applying the database changes. There is no separate "apply migrations" decision — the moment the production service restarts on this build, both migrations in section 6 run.

This is how the two migrations reached the development database. Plan the deployment around it.

One SQL script must run in the same maintenance window as the deploy. grant_crm_lead_assignment_roles_2026_08_24.sql. Without it, every CRM user in production opens the Leads screen and sees nothing at all. Not an error — an empty grid. This is currently the live state of the development environment, because the script has not been run there either.

Cause: lead visibility is now scoped by the CRM_Leads_ViewAll role. The role is created automatically by the seeder but granted to nobody. No lead has an owner yet, so a user without that role matches zero rows.

Everyone must sign out and back in. Security roles are baked into the JWT at login and the token lives for 7 days. Until a user re-authenticates, the new roles do not apply to them and they will still see an empty leads list.

3   Workstream A — CRM bug fixes

3.1   Dead /crm route removed

CRMDashboard.tsx imported a component that does not exist (../form/CreateContractorForm — the real file lives under features/parties/), rendered a hard-coded empty grid, and had a "Create New Lead" button that only set an unused state variable. Nothing linked to it: the header points at /sales-opportunities and the CRM sub-menu never referenced it.

Removed the component and its route. /leads and /sales-opportunities are unaffected and still gated behind CRM_View.

3.2   Opportunity fields were being discarded

CreateSalesOpportunity persisted only stage, project and unit onto the opportunity row. Name, description, estimated amount, currency, probability, close date, next step, data source, campaign and type were written to the history row only and lost from the record itself — which is why the board's value and close-date fields never displayed anything.

Both create and update now persist the full payload. Every assignment on the update path is null-guarded, because the board's drag-and-drop stage change reuses the same command with a sparse DTO — an unguarded write there would have blanked the record.

Not fixed: the opportunity form still does not collect amount, close date or name. Those fields now persist correctly when supplied by the API or an import, but no UI captures them, and the board's currency chip remains commented out. The pipeline still carries no monetary value.

3.3   Cancelled deals never closed

Only DONE_DEAL had any effect, and even that set IS_WON without IS_CLOSED. A cancelled opportunity sat in its original pipeline column indefinitely.

Cancellation actions now close the opportunity, move it to SOSTG_CLOSED_LOST, zero the probability and write a history entry naming the cancellation reason. Done Deal now sets both flags. The same flags are applied when a card is dragged to a closed column, and cleared when dragged back to an open stage — without that, a reopened deal would keep its action form locked forever.

Known residual: winning a deal sets the apartment to APARTMENT_RESERVED, but nothing ever releases it. Reopening or cancelling leaves the unit reserved. Pre-existing behaviour, not introduced here.

4   Workstream B — Lead assignment

Previously there was no way to assign a lead to anyone. A 500-row import landed with every lead belonging to nobody, and no screen or field could change that. The only ownership in the module was on the opportunity, set once a deal already existed — far downstream of where work is actually distributed.

4.1   Data model — no new table

PartyRelationshipType already contained a seeded LEAD_OWNER row, unused, and PARTY_RELATIONSHIP was empty. One active assignment is one row:

ColumnValue
PARTY_ID_FROM / ROLE_TYPE_ID_FROMthe sales rep / SALES_REP
PARTY_ID_TO / ROLE_TYPE_ID_TOthe lead / LEAD
PARTY_RELATIONSHIP_TYPE_IDLEAD_OWNER
FROM_DATE / THRU_DATEassignment window; THRU_DATE null while active

Reassignment closes the open row and opens a new one, so ownership history comes for free. Unassigning closes the row rather than deleting it.

4.2   What users get

  • Assign / reassign / unassign from a row action on the leads grid, with the current owner shown
  • Bulk assign — checkbox selection with select-all-on-page, and a toolbar action. Selection survives paging, because it is held as a set of ids rather than a flag on the row
  • Assign on import — after a batch import, a prompt offers to assign the newly created leads to a rep. CreateLeadsBatch now returns the ids it created so the UI can do this; creation itself still never assigns
  • Owner column on the grid, sortable and filterable server-side
  • Ownership history in the assign dialog — who held the lead, over what window, with the assignment note

Partial-success semantics on bulk assign mirror the existing batch import: per-lead failure reasons, and leads already owned by the target rep are counted separately rather than written twice.

4.3   Two new roles

RoleGates
CRM_Leads_AssignAssign, reassign, unassign, bulk assign, and read assignment history. The CRM Admin's defining permission. Enforced with [Authorize(Roles=…)] on all four endpoints
CRM_Leads_ViewAllSee every lead. Without it a user sees only leads assigned to them. Enforced inside ListLeads as a filter on the IQueryable, so it applies before OData paging — a user cannot page or filter around it

Why this matters beyond these two roles. Before this change, no granular CRM role was read anywhere in the code. CRM_View gated the whole module at the route level and nothing else was checked, so all 13 CRM users were functionally identical despite holding nine roles each. These two are the first CRM permissions that actually do something.

Scoping fails closed: a user who cannot be resolved to a party sees nothing rather than everything. Unassigned leads are visible only to ViewAll holders, which is what makes distribution an admin function.

5   Workstream C — Identity repoint

5.1   The problem

Four audit columns recorded "who did this" as a foreign key into the OFBiz USER_LOGIN table. That table is a hard-coded seed list in SeedContracts.cs, is not used for authentication, and is only partially populated.

MeasureDevelopment
Rows in USER_LOGIN10
Rows in AspNetUsers24
CRM users with a USER_LOGIN row2 of 13 (Emad, Ahmad)

The consequence was silent data loss: an action or history entry written by any of the eleven CRM sales staff recorded a null actor, and the history screen displayed a raw GUID instead of a name. For the new assignment feature it was worse — one of the two designated CRM Admins (rmostafa@gmail.com) has no USER_LOGIN row, so every assignment they made would have recorded nothing, and the foreign key would have rejected any attempt to store their real identity.

5.2   The change

All four columns now reference AspNetUsers(Id) — the table the application actually authenticates against.

TableColumnNew constraint
PARTY_RELATIONSHIPCREATED_BY_USER_LOGINPARTY_REL_CREATED_BY_USER
SALES_OPPORTUNITYCREATED_BY_USER_LOGINSLSOPP_CREATED_BY_USER
SALES_OPPORTUNITY_ACTIONCREATED_BY_USER_LOGINSLSOPPACT_CREATED_BY_USER
SALES_OPPORTUNITY_HISTORYMODIFIED_BY_USER_LOGINSLOPHI_MODIFIED_BY_USER

Column names are unchanged, so no application code outside these handlers is affected. IUserAccessor gained GetUserId(), which reads the id straight off the JWT's NameIdentifier claim. The old three-hop lookup (username → PartyId → UserLoginId) is gone: two database round-trips per write become zero, and the history screen's name lookup collapsed from three queries to one that works for all 24 users.

SALES_OPPORTUNITY_ACTION.CREATED_BY_USER_LOGIN also became nullable. It was previously NOT NULL with the handler falling back to the literal string "SYSTEM", which is not a valid AspNetUsers.Id and would have failed the new foreign key outright. An unresolvable actor now records nothing rather than a fake user.

Step 2 — pre-flight data check

SELECT 'ACTION' AS t, COUNT(*) AS bad FROM SALES_OPPORTUNITY_ACTION a
  WHERE a.CREATED_BY_USER_LOGIN IS NOT NULL
    AND NOT EXISTS (SELECT 1 FROM AspNetUsers u WHERE u.Id = a.CREATED_BY_USER_LOGIN)
UNION ALL SELECT 'HISTORY', COUNT(*) FROM SALES_OPPORTUNITY_HISTORY h
  WHERE h.MODIFIED_BY_USER_LOGIN IS NOT NULL
    AND NOT EXISTS (SELECT 1 FROM AspNetUsers u WHERE u.Id = h.MODIFIED_BY_USER_LOGIN)
UNION ALL SELECT 'OPPORTUNITY', COUNT(*) FROM SALES_OPPORTUNITY s
  WHERE s.CREATED_BY_USER_LOGIN IS NOT NULL
    AND NOT EXISTS (SELECT 1 FROM AspNetUsers u WHERE u.Id = s.CREATED_BY_USER_LOGIN);

Production is likelier than development to contain rows written by the eleven CRM staff who have no USER_LOGIN entry — but those recorded null, not a bad id, so they pass. A non-zero count means a real USER_LOGIN_ID that does not match any ASP.NET user.

8   Rollback

The database changes are not cleanly reversible by restarting an older build. EF does not un-apply migrations on startup — rolling the code back leaves the schema forward. Plan to roll forward, or restore from the step 1 backup.

8.1   Reversing the roles only

The least destructive intervention. If the leads screen misbehaves, granting CRM_Leads_ViewAll to everyone restores pre-deployment visibility without touching schema. The grant script takes its own backup table (AspNetUserRoles_bak_20260824) and documents the restore statement.

8.2   Reversing the schema

Each migration has a generated Down. One caveat on RepointActorColumnsToAspNetUsers: reverting restores SALES_OPPORTUNITY_ACTION.CREATED_BY_USER_LOGIN to NOT NULL, so EF first rewrites any null actor to an empty string — and '' is not a valid USER_LOGIN_ID, so the restored foreign key would then reject those rows. EF flagged this at scaffold time as a possible data-loss operation. Treat the Down as a last resort.

8.3   MySQL does not do transactional DDL

The generated scripts wrap statements in START TRANSACTION … COMMIT, but each ALTER commits implicitly. If a later statement fails, earlier ones are already applied. This is precisely why the step 2 pre-flight check matters.
