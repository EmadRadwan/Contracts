1   Scope and method

This covers the 24 August release only. It does not re-test the wider CRM module — that is CRM-Module-Test-Plan.pdf. Four things shipped:

  • Lead assignment — leads can now be owned by a sales rep, individually or in bulk
  • The CRM Admin split — four roles that, for the first time in this module, actually restrict what a user can do: assigning, seeing all leads, creating leads and editing them
  • Identity repoint — audit columns moved from the OFBiz USER_LOGIN table to AspNetUsers
  • Three CRM fixes — a dead route, discarded opportunity fields, and cancelled deals that never closed
  • Validation alignment — the lead form and the Excel import now demand the same fields

Work each suite top to bottom; later steps depend on records created earlier. Database checks are given inline. Suites F and G are the two that matter most — F is the only security boundary in the release, and G is the fix that was silently losing data before.

9   Suite G — Identity repoint critical

9.1   Why this suite exists

Four audit columns used to reference the OFBiz USER_LOGIN table, which holds only 10 rows against 24 application users — and covers just 2 of the 13 CRM users. Anything done by the other eleven recorded a null actor, and the opportunity History tab showed a raw GUID instead of a name.

Use Ayman for this suite, not Emad. Emad has a USER_LOGIN row, so his actions would have been recorded correctly even before the fix — testing with him proves nothing. Ayman has none. If his actions now record an actor, the repoint works.

#StepExpected result✓
G1Sign in as Ayman. Assign a lead to any repSucceeds☐
G2Check the actor was recordedFirst query below returns Ayman's AspNetUsers.Id — not null☐
G3Open that lead's ownership historyThe entry shows a "by" attribution rather than omitting it☐
G4As Ayman, create a sales opportunitySaves successfully. Before the repoint this would have failed the foreign key outright☐
G5As Ayman, log an action on an opportunitySaves; appears in the comment feed☐
G6As Ayman, change an opportunity's stage, then open the History tabThe entry shows Ayman's display name, not a GUID and not blank. This is the headline fix☐
G7Check the stored valuesSecond query below — all four columns hold real AspNetUsers.Id values☐
G8Confirm older records still displayHistory rows written before this release still render; their attribution resolves for Emad and Ahmad☐
G9Confirm the foreign keys point at the right tableThird query — four constraints, all referencing AspNetUsers☐
 
-- G2: who performed the most recent assignment
SELECT pr.PARTY_ID_TO, pr.CREATED_BY_USER_LOGIN, u.UserName
FROM PARTY_RELATIONSHIP pr LEFT JOIN AspNetUsers u ON u.Id = pr.CREATED_BY_USER_LOGIN
WHERE pr.PARTY_RELATIONSHIP_TYPE_ID='LEAD_OWNER' ORDER BY pr.FROM_DATE DESC LIMIT 3;

-- G7: no orphaned actor values anywhere (all three must be 0)
SELECT 'ACTION' t, COUNT(*) bad FROM SALES_OPPORTUNITY_ACTION a WHERE a.CREATED_BY_USER_LOGIN IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM AspNetUsers u WHERE u.Id=a.CREATED_BY_USER_LOGIN)
UNION ALL SELECT 'HISTORY', COUNT(*) FROM SALES_OPPORTUNITY_HISTORY h WHERE h.MODIFIED_BY_USER_LOGIN IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM AspNetUsers u WHERE u.Id=h.MODIFIED_BY_USER_LOGIN)
UNION ALL SELECT 'OPPORTUNITY', COUNT(*) FROM SALES_OPPORTUNITY s WHERE s.CREATED_BY_USER_LOGIN IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM AspNetUsers u WHERE u.Id=s.CREATED_BY_USER_LOGIN);

-- G9: the four constraints
SELECT TABLE_NAME, CONSTRAINT_NAME, REFERENCED_TABLE_NAME
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE CONSTRAINT_NAME IN ('PARTY_REL_CREATED_BY_USER','SLSOPP_CREATED_BY_USER',
                          'SLSOPPACT_CREATED_BY_USER','SLOPHI_MODIFIED_BY_USER');

12   Known limitations — do not raise these

BehaviourWhy
Unassigning records no actorIt closes a row rather than creating one, so there is nowhere to store the acting user. You can see who assigned a lead, never who removed it
No automatic distributionNo round-robin, territory rules or assignment notifications. Distribution is manual by design in this release
Reassigning a lead does not change its opportunity ownerDeliberate — a deal keeps its closer
Regular users cannot see unassigned leadsIntended. Only ViewAll holders see the unassigned pool
Opportunity form still captures no amount or close datePersistence was fixed; the UI fields were out of scope
Won deals never release the apartmentPre-existing; cancelling or reopening leaves the unit reserved
Some legacy CRM roles still do nothingCRM_Leads_View, CRM_Leads_Delete and the CRM_Contacts_* family remain unread by the code — there is no Contacts screen and no delete function anywhere in CRM. Five roles are enforced: CRM_View, CRM_Leads_Create, CRM_Leads_Edit, CRM_Leads_Assign, CRM_Leads_ViewAll
Bulk assign stamps one timestamp across all rowsA bulk of 50 and 50 individual assignments look identical in history
